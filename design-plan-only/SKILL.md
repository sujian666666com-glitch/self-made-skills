# Design Plan Only

只分析任务并输出一份可执行、可评审的设计方案，不实施方案。默认仅在当前对话中以文字形式输出，不写入任何文件。

## 默认输出与行为边界

- 默认交付形式为当前对话中的文字方案，可使用 Markdown 排版；不创建方案文件或其他落盘产物。
- 最终只输出方案正文，以及「分支基线检查」要求的提醒；不添加执行结果、后续邀请或无关说明。
- 不创建、修改、移动或删除文件，不改变代码、配置、数据库、服务或环境。
- 不运行构建、测试、部署或数据库操作，不调用任何会改变外部状态的工具。
- Git 仅允许 `fetch` 更新远端跟踪引用等元数据，以及 `status`、`log`、`diff`、`show`、`blame`、`rev-parse`、`merge-base` 等只读查询；不执行 `rebase`、`merge`、`pull`、`checkout`、`stash`、`commit` 等改动工作区、索引或分支的操作。
- 不创建 OpenSpec、任务单或计划文件。
- 仅可使用对话中已有信息，以及为核对事实所必需的最小只读检索或文件查看。
- 不把推测写成事实，不虚构文件、接口、字段、数据表或现有行为。
- 不声称已经修改、执行、验证或测试通过。
- 用户在显式调用本 Skill 时同时要求实施，仍只输出方案。

## 分支基线检查

- 任务涉及可访问的现有仓库时，在核对文档与代码之前，先确认当前分支是否已包含远端 `develop`（默认 `origin/develop`）的最新提交：先 `git fetch origin develop` 更新远端跟踪引用，再用 `git merge-base --is-ancestor origin/develop HEAD` 判断；未包含时用 `git rev-list --count HEAD..origin/develop` 与 `git log -1 origin/develop` 取得落后提交数和远端最新提交。涉及多个仓库时逐一检查。
- 已包含时不额外说明，直接进入调研。
- 未包含时，在方案正文之前用一到两行提醒用户：当前分支落后于远端 develop 的提交数与远端最新提交，方案基于当前分支的代码现状，建议用户自行同步后再评审或实施；不自动执行 rebase、merge 或 pull。
- 不是 Git 仓库、不存在 `origin/develop`、`fetch` 失败（如无网络或无权限）等无法验证的情况，同样在方案正文之前明确说明未能验证及原因，不默认视为已同步；`fetch` 失败但本地已有 `origin/develop` 时，可按本地引用比较，但须说明该引用未更新、结论可能过期。

## 信息不足

- 能合理继续时，标明“假设”和“待确认事项”后直接给出方案。
- 只有缺失信息会使方案方向发生实质变化且无法合理假设时，才提出最少量的关键问题。
- 任务涉及可访问的现有仓库时，先用最小只读检索核对具体代码路径；仓库不可访问或尚未创建时，明确标注“路径待确认”，不猜测实现位置。

## 设计与开发原则

生成的方案必须明确约束后续开发始终遵守以下原则：

1. **优先复用**：动手前先检索现有代码。已有接口、数据模型、工具函数或模块能够满足需求时，一律复用或做最小化扩展，禁止重复造轮子或另起平行实现；确需新增时，必须说明现有实现不可复用的具体原因。
2. **保持整洁**：接口定义、代码结构、数据库设计和实现代码必须整洁、一致、可读，命名清晰、职责单一，不引入或遗留冗余字段、死代码和临时补丁。
3. **架构清晰、拒绝过度设计**：采用满足当前需求的最简单直接方案，不引入不必要的抽象层、设计模式、预留扩展点，也不为假想的未来需求增加复杂度。
4. **测试克制**：测试只覆盖核心业务逻辑和关键路径，以最少的用例证明行为正确；不堆砌防御性安全检查、异常探测、预警类断言，也不为极端边界情况编写冗余用例。
5. **调研有据**：代码调研必须同时核对仓库内相关文档（如 README、设计文档、接口说明、任务记录）和实际代码，不凭记忆或假设下结论；文档与代码不一致时以代码为准，并明确指出差异。

## 生成方法

在内部完成以下分析，不输出推理过程：

1. 识别要解决的问题、预期行为变化和非目标。
2. 识别涉及的仓库、仓库边界及各自承担的职责。
3. 按「分支基线检查」确认各可访问仓库的当前分支是否已包含远端 develop 最新提交，再开始核对代码。
4. 同时核对仓库内相关文档和实际代码，确认具体路径、当前行为及文档差异，区分事实、目标设计、假设、依赖和待确认事项。
5. 盘点可复用的接口、数据模型、工具函数和模块，确定复用或最小扩展方式；确需新增时记录不可复用原因。
6. 提取与任务直接相关的业务、架构、安全和兼容性约束。
7. 按依赖顺序设计最简单直接的最小充分实施路径，避免平行实现、冗余结构和过度抽象。
8. 将核心业务逻辑和关键路径映射到最少量的可执行测试，并定义客观的完成标准。

## 固定输出格式

# 设计方案：<任务名称>

## 一、目标

- 需要解决的问题与预期行为变化。
- 本次明确不处理的范围。

## 二、涉及仓库

- 逐项列出与任务直接相关的仓库名称或根路径，以及该仓库承担的职责。
- 不将仅用于参考、原型或部署依赖但无需修改的仓库计入实施范围；无法确认时明确标注待确认。

## 三、上下文

- 当前现状、问题和涉及的模块、服务、接口、数据或页面。
- 列出已经只读核对的仓库文档和具体代码文件或目录路径，并说明各路径的当前职责；未核对的路径不得写成事实。
- 文档与代码不一致时，以代码现状为准并明确列出差异。
- 说明目标设计，包括复用或最小扩展决策、关键模块分工、数据流或调用链、读写边界及异常处理，并与已有行为明确区分；确需新增实现时说明现有实现不可复用的原因。
- 已知依赖与已有行为。
- 必要时列出假设和待确认事项。

## 四、约束

- 只列与当前任务有关的业务、技术、安全、权限、兼容性和范围约束。

## 五、实施计划

按实际依赖顺序列出步骤，优先指向已有接口、数据模型、工具函数或模块的复用与最小扩展。每个关键步骤说明处理对象、设计方式、输入输出或数据流、异常边界及对现有功能的影响；确需新增时说明不可复用原因，避免“修改后端”“补充测试”等空泛表述。

## 六、测试与完成标准

- 测试只覆盖核心业务逻辑和关键路径；异常、权限、边界、兼容性或回归场景仅在其直接影响核心行为或需求明确要求时纳入。
- 使用最少量的用例证明行为正确，不堆砌防御性安全检查、异常探测、预警类断言或极端边界冗余用例。
- 关键测试写明前置条件、操作或输入以及预期结果。
- 最后列出可客观判断的完成条件，不得写成已经执行或已经通过。

默认保持简洁；内容必须针对当前任务，不能只复述模板。
